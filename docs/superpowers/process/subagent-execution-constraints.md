# CelanWorksmith Subagent 执行通用约束

## 目的

本约束适用于 CelanWorksmith 后续所有由 Subagent-Driven Development 执行的设计、实现、审查和修复任务。目标是在保持独立审查质量的同时，限制单个 Agent 的工作边界，避免长时间探索、上下文漂移、共享工作区冲突和无限修复循环。

## 1. 任务粒度

- 一个代码实现任务只交付一个可独立验证的功能切片；不得将多个无直接依赖的 Widget、交互和数据链路合并到同一个任务。
- 通常限制为不超过 2-4 个生产文件和 1-3 个测试文件。超过该范围时，计划必须说明不可拆分的原因；否则拆分任务。
- 任务 brief 必须包含目标、明确不做的范围、所依赖的既有接口、定向验收用例和完成定义。
- 例如，FilterList 的设计系统控件改造、枚举/Link 条件输入和 Query 模式边界提示应分别作为独立任务执行。

## 2. 并行与工作区

- 对同一工作区的生产代码修改严格串行执行：`brief -> implementer -> scoped review -> fix/re-review -> ledger`。
- 只读代码调查、依赖分析、测试可行性研究和文档审查可以并行，但不得修改生产代码、测试、锁文件或构建产物。
- 确有并行编码需要时，必须使用独立 Git worktree，且各任务修改文件与接口边界不重叠；集成前进行显式冲突审查。

## 3. 测试与验证边界

- 每个代码任务只运行本任务的定向 Jest 测试、相关格式化/ESLint 检查和 `git diff --check`。
- 浏览器手工验证、跨 Widget 集成回归和全仓检查仅作为阶段门禁执行一次，不作为每个短任务的默认门禁。
- 测试基础设施（例如 Page DSL、Canvas 或 DataTree harness）必须单列为任务并先完成；普通功能任务不得隐式承担新建完整测试基础设施的责任。
- 已知无法通过的仓库级检查必须记录原因和影响范围，不能被当作当前任务失败的依据，也不能被标记为已通过。

## 4. Agent 上下文与报告

- 实现 Agent 只读取任务 brief、必要接口定义和与其修改范围相关的 ledger 条目；不得要求其消化完整项目历史或整个计划。
- Prompt 中提供 brief 路径和报告路径，不粘贴长篇历史记录；详细结论写入任务报告文件，Agent 返回状态、提交/变更、测试摘要和 concern 四项简报。
- 每个计划维护独立 `.superpowers/sdd/<plan>/progress.md` ledger。任务启动前必须检查 ledger，已完成任务不得重复派发。

## 5. 时间盒与阻塞处理

- 实现 Agent 若在约 15 分钟内无法进入定向测试阶段，应停止探索并报告 `BLOCKED`，说明已定位文件、阻塞原因、已尝试内容和建议拆分方案。
- `BLOCKED` 不得以相同宽泛任务原样重试；协调者必须缩小任务、补齐前置基础设施或提升模型能力后再派发。
- 审查修复最多五轮。五轮后必须裁决：阻塞核心契约的问题上报并停止；非承重问题写入 ledger 并建立后续任务，不无限重试。

## 6. 模型与审查策略

- 1-2 文件且规格完整的机械改动使用快速模型；Widget、Redux、Saga、DataTree 等跨文件集成使用标准模型；架构决策和阶段最终审查使用高能力模型。
- 每次派发必须显式指定模型层级，避免无意继承高成本默认模型。
- Reviewer 只审查当前任务的 review package/diff，不重复运行 implementer 已验证的同一测试，也不开展无边界的全仓审查。
- 仅 Critical 与 Important 发现进入修复轮；Minor 发现记录到 ledger 或后续计划，除非它直接影响当前任务验收。

## 7. 阶段完成条件

- 每个任务先完成代码与定向审查，再进入下一个依赖任务。
- 每个阶段结束时统一执行跨任务审查、集成验证和手工测试，并建立验证记录与 Git 检查点。
- 出现运行环境问题（服务不可用、上游网络、既有依赖缺失）时，先记录为环境阻塞；不得将环境波动误判为功能实现结论。

## 8. 适用关系

本文件补充而不替代 `subagent-driven-development` skill 的流程要求。发生冲突时，以 Skill、项目计划中的明确验收条件及当前阶段契约为准；本约束用于将这些要求落实为 CelanWorksmith 的日常执行边界。
